## 1. Ціль (навіщо це бізнесу)
Meta має надійно отримувати події `PageView` / `landing_page_view` / `Lead` з
`ksiegowosc.gryphongroup.pl` для максимально дозволеної РОДО частки відвідувачів.
Зараз алгоритм Meta «сліпий» — не бачить воронку, не вчиться, зливає бюджет на
кліки, що нікуди не ведуть за трекінгом.

## 2. Діагноз (з реальних даних Meta API, період 6 чер – 5 лип 2026)
- Витрачено **585,15 PLN**, **228 кліків по посиланню → лише 9 landing_page_view (3,9%)**
  при нормі 60–80%. Заявок пікселем — 3.
- Так не буває органічно: заявка без перегляду сторінки неможлива. Отже трекінг б'є мимо.

### Знайдені причини (в коді)
1. **Головна: піксель загейчений за cookie-згодою, а приймають одиниці.**
   `landing/index.html` рядки ~775–801: піксель вантажиться `loadPixel()` лише якщо
   `localStorage['gg_consent']==='granted'` або після кліку «Прийняти» в cookie-банері
   (`#cookieAccept`). Хто не натиснув — `PageView` не стріляє. 3,9% ≈ частка тих, хто
   натиснув «Прийняти». Той самий гейт у `landing/kalkulator.html` (~983–1000).
2. **Нестиковка на сторінці подяки.** `landing/dziekujemy.html` рядки 125–133:
   піксель + `fbq('track','Lead')` викликаються **без гейта згоди** і використовують
   змінні `PIXEL_ID` та `IS_LOCAL`, яких на цій сторінці **не оголошено** (вони є лише
   в `index.html`). Наслідок: або `ReferenceError` і головна конверсія `Lead` не
   спрацьовує взагалі, або стріляє без згоди — порушення РОДО. Треба усунути обидва ризики.
3. **Перевірити URL призначення оголошень** — чи ведуть точно на сторінки з пікселем,
   без проміжних редіректів, що зривають `PageView`.

## 3. Що зробити (по кроках)
1. **Підтвердити гіпотезу цифрою.** Тимчасово залогувати співвідношення
   згода/відмова (accept vs decline банера) — переконатися, що низький accept-rate і є
   причиною. Прибрати лог після перевірки.
2. **Перевірити, що піксель взагалі коректний,** коли згоду дано: Meta Events Manager →
   Test Events + Meta Pixel Helper на живій сторінці. Зафіксувати, що при `granted`
   летять `PageView`, `ViewContent`, `Lead`.
3. **Полагодити `dziekujemy.html`:** винести оголошення `PIXEL_ID` та `IS_LOCAL` так,
   щоб вони існували на КОЖНІЙ сторінці (спільний скрипт/inline), і підпорядкувати
   `Lead` на подяці тій самій логіці згоди, що й решта (не стріляти без `granted`).
   Уся логіка пікселя має бути в одному спільному місці, а не тричі скопійована.
4. **Підняти легальну частку трекінгу (без порушення РОДО):**
   покращити cookie-банер — зробити кнопку «Прийняти» помітнішою, текст користь-
   орієнтованим, банер не нав'язливим; АЛЕ кнопка «Відхилити» лишається рівноправною,
   без dark patterns. Мета — чесно підняти accept-rate, а не обійти згоду.
5. **Conversions API — вже підключено, будувати НЕ треба.**
   На кабінеті увімкнено вбудований Meta **«Conversions API for Web»** (Supported by Meta),
   активований власницею 27.06.2026. Він автоматично дублює події пікселя на серверний
   бік (набори Księgowość + Legalizacja). Живиться з того самого пікселя → фікс банера
   (крок 4) годує і його. Жодного коду в Apps Script для цього не потрібно.
   ⚠️ Нюанс: цей Web-CAPI теж тригериться браузером, тобто теж лише ПІСЛЯ згоди на cookie.
   Ловити `Lead` НЕзалежно від cookie-згоди можна лише окремим server-side CAPI прямо з
   приймача форм — це ОКРЕМЕ РОДО-рішення (§7), не робити без підтвердження.
6. **Категорія набору даних = «Немає» → лишити як є (перевірено 06.07.2026).**
   Редактор категорії пропонує ВИКЛЮЧНО чутливі категорії GDPR (економічна вразливість,
   здоров'я, національність, раса, релігія, сексуальність, профспілка) — варіанту «жодна
   не підходить» немає. Для бухгалтерії жодна не застосовна, а вибір будь-якої лише
   ПОСИЛИВ би обмеження Meta на ці дані. Тому категорію НЕ призначати — «Немає» і є
   правильний стан. Попередження «обмеження на передавання даних» — це базова обережність
   Meta (Core Setup), а не наслідок відсутньої категорії; цим редактором воно не знімається.
7. **Звірити посилання оголошень** із фактичними URL сторінок із пікселем.
8. **Домен `invalid.invalid`** у списку сайтів набору — артефакт подій без валідного
   `event_source_url` (сипались, доки піксель був заблокований згодою). Має само вилікуватись
   у міру реального трафіку зі згодою — перевірити за 3–5 днів, окремо не чіпати.

## 4. Критерій готовності (acceptance)
- Test Events показує `PageView` і `Lead` при наданій згоді на всіх 3 сторінках.
- `dziekujemy.html` більше не кидає `ReferenceError`; `Lead` не стріляє без згоди.
- Співвідношення клік→`landing_page_view` для сегмента зі згодою підіймається до
  ~40–70% (а не 3,9% по всіх).
- Один спільний блок коду пікселя, без потрійного дублю.
- (CAPI — Meta Web-CAPI вже активний і сам дедуплікує серверну копію з піксельною.)
- (Категорія набору — лишається «Немає»; це правильний стан для бухгалтерії, див. §3 крок 6.)

## 5. Як перевірити (verification)
- Meta Events Manager → Test Events: пройти шлях відвідувача (прийняти cookie →
  переглянути → відправити форму → сторінка подяки) і побачити всі події.
- Meta Pixel Helper (розширення Chrome) на проді: PageView присутній після згоди,
  відсутній до згоди.
- Через 3–5 днів після деплою — повторно смикнути Meta API (`act_1400520141168551`,
  скрипт у `D:\PROJECTS\ai-ads-agent`): співвідношення клік→LPV має зрости.

## 6. Обмеження (РОДО — не порушувати)
- **НЕ вантажити маркетинговий піксель до згоди.** Ніякого implied consent / згоди
  «за замовчуванням» / прихованого автозапуску. Це вимога РОДО і правило власника.
- Обов'язковий чекбокс згоди у формі лишається `required`; маркетинговий — окремий,
  вимкнений за замовчуванням.
- РОДО-тексти й дані адміністратора не вигадувати — брати з `D:\PROJECTS\RODO\`.
- У прод не пушити без підтвердження людини.

## 7. Рішення для людини (не робити самому — ескалувати)
Технічний ремонт підніме трекінг лише в межах тих, хто дав згоду (стеля ~частка
accept). Якщо потрібен максимум заявок незалежно від cookie-згоди на сайті — розглянути
перенесення оголошень на **Meta Lead Form (миттєва форма всередині Facebook)**: трекінг
і збір заявки відбуваються в Meta, стик реклама→сайт зникає. Це маркетингове рішення
власника, не технічне — винести окремо.
